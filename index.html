Algorithm Walkthrough

  1. Bounding Box Calculation: Given three vertex coordinates \((x_0, y_0)\), \((x_1, y_1)\), and \((x_2, y_2)\), I first compute the minimum and maximum $x$ and $y$ bounds. I use std::floor and std::ceil to snap the float coordinates to integer pixel indices, establishing a tight axis-aligned bounding box around the triangle.
  2. Pixel Loop & Center Sampling: I iterate through every integer pixel position \((x, y)\) inside the bounding box. As specified, sample points are evaluated at the pixel center: \((x + 0.5, y + 0.5)\).
  3. Line Function Evaluation: For each center sample, I evaluate the three implicit edge/line functions: \[ L_i(x, y) = -(x - x_i)(y_{i+1} - y_i) + (y - y_i)(x_{i+1} - x_i) \]
  4. Winding Order & Inside Test: To handle both counter-clockwise (CCW) and clockwise (CW) vertex orderings, I check whether all three edge functions are concurrently non-negative (\(L_0 \ge 0 \land L_1 \ge 0 \land L_2 \ge 0\)) OR non-positive (\(L_0 \le 0 \land L_1 \le 0 \land L_2 \le 0\)).
  5. Pixel Filling: If the sample passes the test (including lying directly on a boundary edge), I call fill_pixel(x, y, color) to rasterize the pixel.

Algorithm Efficiency

My implementation is no worse than an algorithm that checks each sample within the bounding box because the iteration bounds (min_x to max_x and min_y to max_y) are constructed explicitly from the minimum and maximum coordinates of the triangle's vertices. Rather than checking every pixel across the entire screen framebuffer (which scales with total display resolution), the nested loops strictly visit pixels within \([\lfloor \min(x_i) \rfloor, \lceil \max(x_i) \rceil] \times [\lfloor \min(y_i) \rfloor, \lceil \max(y_i) \rceil]\). Thus, the total number of tested samples scales directly with the bounding area of the triangle itself.
